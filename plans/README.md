## Findings considered and rejected

- **"Build push notifications" (original direction item): mostly already built.**
  The repo has `NotificationService`, `FirebaseMessagingService`, device-token
  sync, a `supabase/functions/send-push/` edge function, DB triggers in
  `20260526000003_notification_triggers.sql` (swap requests, meeting notes, hour
  updates, continuous events), and native Firebase config files. The only real
  client gap was that `scheduleEventReminder` is never called — that became Plan
  007. No greenfield push build is warranted.
- **Hardcoded Supabase anon key in `main.dart`: by design.** It is the public
  anon key, documented as intentional in `CLAUDE.md`. Not a finding.
- **`BuildContext` used across async gaps (pervasive analyzer info):** benign
  given the dialog/snackbar usage patterns; not worth a dedicated plan. Address
  opportunistically (some plans add `mounted` guards in passing).
- **Unbounded list fetches (home/admin load all events + slots + attendees):**
  fine at NHS-chapter scale; revisit only if societies grow large. Not worth doing now.

## Not selected this round (available to plan later)

- **Verification baseline (tests + CI):** the highest-leverage *unblocker* — a
  34K-LOC shipping app with no tests and no CI. Every plan here leans on `flutter
  analyze` only because of this gap. Strongly recommended as the next thing to plan.
- **Authorization / RLS verification (security):** destructive admin actions
  (delete events, bulk-delete service hours) are gated client-side by `isAdmin`;
  whether Supabase RLS enforces society-scoped admin writes server-side could not
  be verified from the repo. Worth an investigation plan: audit RLS policies on
  `Events`, `"Service hours"`, `Attendees`, `swap_requests`.
- **Error-handling pass:** ~126 `catch` blocks mostly just log; wiring a crash
  reporter (Firebase Crashlytics — `firebase_core` already present) and surfacing
  user-facing errors on critical paths is a good follow-up to Plan 004.
